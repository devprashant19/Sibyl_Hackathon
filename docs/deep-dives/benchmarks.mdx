When introducing chaos into your production environment, the reliability of the chaos engine itself is paramount. If a test runner leaks state between tests, or if one tenant starves another's CI pipeline, the engine becomes a liability rather than a safety net.

We continuously run a rigorous distributed load-testing suite against the Sibyl platform (`packages/core/test/load-test.ts`) to assert three critical guarantees.

## 1. Absolute Isolation (0% Event Leakage)
A common problem in naive chaos engines is asynchronous event leakage—a network fault injected in Sandbox A accidentally impacts Sandbox B because the global state wasn't perfectly isolated.

**The Benchmark:**
We simultaneously spawn **1,000 concurrent simulation runs**. Each run executes a synthetic target app that attempts to race network faults against the control plane aggregator.

**The Result:**
- **Leakage Rate:** 0.00%
- **Guarantee:** Sibyl uses true Docker-in-Docker isolation and strict run-scoped HTTP headers for telemetry aggregation. A fault injected in run `A` mathematically cannot affect run `B`.

## 2. Multi-Tenant Queue Fairness
If you have multiple development teams in your organization, Team A triggering a massive 10,000-run Monte Carlo simulation shouldn't stall Team B's simple 5-run CI check.

**The Benchmark:**
We bombard the BullMQ task queue with 10,000 runs from `Tenant_A`. One second later, we submit 10 runs from `Tenant_B`.

**The Result:**
- **Tenant_B Wait Time:** ~1.2 seconds.
- **Guarantee:** Sibyl employs a strict **Round-Robin Fair Scheduler** at the tenant level. Instead of a strict FIFO queue that allows starvation, the worker fleet pulls evenly across all active tenants, ensuring your CI checks stay lightning-fast even during heavy organization load.

## 3. Elastic Autoscaling
When a complex Bayesian optimization search kicks off, queue depth can spike rapidly.

**The Benchmark:**
We artificially freeze the worker fleet, allowing queue depth to spike to 5,000 pending runs. We then unfreeze the fleet and monitor the Autoscale Controller's reaction time.

**The Result:**
- **Recovery SLA:** The queue completely drains within the expected metric ticks, scaling the virtual worker fleet aggressively by 20% increments until stability is reached.
- **Guarantee:** You will never pay for idle chaos infrastructure. The `Sibyl-Worker` fleet scales directly on the `sibyl.queue.depth` OpenTelemetry metric, spinning down to exactly 0 when idle.
