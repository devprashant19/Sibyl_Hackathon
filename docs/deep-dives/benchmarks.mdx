This page previously reported results for 1,000 concurrent Docker-sandboxed runs, multi-tenant queue
fairness and autoscaling. Those numbers did not come from any test in the repository — the sandbox
entrypoint and the job producer they depend on do not exist — and have been removed. What follows is
what is actually measured.

## Run isolation within one process

Concurrent runs share a process, so isolation is a property of the engine, not of containers:

- **Fault decisions** resolve the active run's engine through `AsyncLocalStorage`; each run has its own
  seeded streams.
- **Time** is routed per run: under `--concurrency`, `Date.now()` and `setTimeout` inside run A use run A's
  virtual clock, and outside any run they use real time.

`packages/core/test/regressions.test.ts` runs four timer-based workflows two at a time on accelerated
clocks and asserts each observed exactly its own 60 s of virtual time, the session finished in under 2 s of
wall time, and the process's native timers were restored afterwards.

Isolation does **not** extend to application state your workflow shares (module-level variables, a shared
database). Key such state by `AsyncContext.getRunId()`.

## Determinism

`pnpm test:drivers` runs property tests that execute the same workload twice per driver under the same
seed and assert identical captured events, with exact expected counts so an empty timeline cannot pass.
`pnpm smoke` checks that the same seed finds the same number of failures in a fresh process.

## Not yet measured

Throughput (runs per second) and scaling with `--concurrency` depend heavily on the workflow and are not
benchmarked. The distributed worker is scaffolding, so there are no queue or fleet measurements.
